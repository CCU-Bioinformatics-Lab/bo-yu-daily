## 為什麼不算真值樹（原文證據）

1. **樹不是從單細胞建出來的。** 演化樹的流程是 bulk 短讀 VAF → FACETS → PyClone-VI → ClonEvol（主文 Methods；supplement Fig. S9）。
2. **scDNA 只做了兩件事。** 第一，用 Manhattan distance + complete linkage 對 CN profile 做階層分群（主文 Methods）。這個 dendrogram 是 CN 相似度分群，不是 SNV 演化樹。第二，檢查每個細胞有沒有 mutant reads。
3. **原文用詞是「validate」。** 原文寫 scDNA "was performed in two representative cases to further validate the inferred clonal structures"，意思是驗證推論出來的結構，不是提供真值。
4. **長讀選樹的病人和做 scDNA 的病人不同。**
   - 長讀用來選 topology 的唯一例子是 S14。作者用同一條 read 上的突變先後選了 linear model，捨棄 branched model（supplement Fig. S9c–d 和 Note）。

> **為什麼只產 HTML**：原本同時產一份 Markdown，理由是 GitHub 網頁點 `.html` 只顯示原始碼、
> 點 `.md` 才渲染得出來。但兩份內容一樣，**同一件事有兩個入口**——讀者要問哪份才是準的，
> 而給 agent 讀的需求已經由 `.data/<date>.json` 滿足（有語意欄位，比剖 Markdown 更直接）。
> 現在只留 HTML（讀者要求的格式）＋ JSON（事實來源）。
> 取得 HTML 的方式寫在日誌 repo 的 `README.md` 裡（clone 或 Download ZIP）。

## 四個分支

| 使用者輸入 | 做什麼 |
|---|---|
| `/daily-log`（無參數） | **從全域游標掃到現在**。落在哪個檔由游標起點的日曆日決定；該檔已存在就增補 |
| `/daily-log 2025-01-15` | 補寫指定日期（整個日曆日）。**不動游標** |
| `/daily-log --force` | 忽略游標，從今天 00:00 重掃（既有 items 全部取代）。前一次記錯了才用 |
| `/daily-log --rebuild` | **不掃描、不問**，只跑 `render.py --all` 把所有 JSON 重渲染。改完 CSS 或版面時用 |
| `/daily-log --demo <日期>` | **示範用**：走完整流程，但寫進 demo 目錄，真實 repo 一個字都不碰 |

`--rebuild` 直接跑腳本就結束，不要走下面的流程。

**這個 skill 是全自動的**：跑完印出候選表就結束，不問任何問題。
候選表是給使用者**事後稽核**用的，不是等他回答。
他主動要改時，改 JSON 重渲染即可（秒級），不必重跑掃描。

### `--demo` 模式

對人示範這個 skill 怎麼跑時用。**補寫模式（`/daily-log <過去某天>`）會覆蓋掉那天
已經交出去給人看過的日誌**，示範時絕不能用它。

**兩種寫法擇一，不要同時用**（同時用不會出錯，但只有一種是必要的）：

| 寫法 | 產出去哪 |
|---|---|
| `collect_day.sh --demo <日期>` | 正式 repo 旁邊的 `<repo>-demo`（自動推導） |
| `DAILY_LOG_REPO=<demo 路徑>` | 你指定的那個路徑 |

⚠️ 後續步驟（`validate_log.py` / `verify_evidence.py` / `render.py` /
`check_readability.py`）**只認環境變數**，所以不管用哪種寫法，
那幾步都要帶 `DAILY_LOG_REPO=<demo 路徑>`。

做法：把 `DAILY_LOG_REPO` 指到 demo 目錄，**掃描與渲染兩步都要帶**（`render.py` 也讀這個環境變數）：

```bash
DEMO=/path/to/your-daily-demo
DAILY_LOG_REPO=$DEMO bash .claude/skills/daily-log/scripts/collect_day.sh <日期>
# …Step 2-1~4 照常，JSON 寫進 $DEMO/.data/<日期>.json …
DAILY_LOG_REPO=$DEMO python3 .claude/skills/daily-log/scripts/render.py <日期>
```

- 游標檔也在 demo 目錄底下，所以**真實游標不受影響**
- demo 目錄不是 git repo，產出可以隨時刪掉重來
- ⛔ 示範完不要把 demo 產出複製回真實 repo

### 全域游標

掃描區間**不再是「該日曆日 00:00~23:59」**，而是「上次讀到哪 → 現在」，
斷點記在日誌 repo 的 `.data/_cursor.json`。

**為什麼改**：舊版把斷點存在該日的 `.data/<date>.json` 裡，每天各自一個、彼此不連續 ——
你寫完日誌之後又繼續做的那段，昨天的掃描已結束、今天從 00:00 起算，**兩邊都不涵蓋**。
原始場景實測連續五天，每天漏 0.8~3.4 小時，累計約 **11 小時的工作從沒被任何掃描讀過**，而且無聲無息。

**連帶效果**：午夜不再是邊界。凌晨兩點的工作自然接在昨天下午後面 ——
若你的活動高峰橫跨午夜（原始場景是 00:00~03:00，每天約 2,400 則訊息），
舊的日界等於切在工作最密集的地方。

**日期標籤只是檔名。** `.data/2025-01-15.json` 不保證內容剛好落在 1/15 那個日曆日；
實際涵蓋區間由 `covers` 欄位記錄，並顯示在頁面上。不要為了讓標籤「精準」去調區間。

**跨日 session 不需要特別處理** —— 過濾是逐則訊息比對時間戳，session 從來不是抓取單位。

## 流程

每個階段只定義自己的 **exit gate**（做完的條件）。
第 N 階段的 exit gate 就是第 N+1 階段的開始資格，下一階段不重做同一組檢查。
**gate 沒過就留在原地修，不要往下走。**

| Step | 做什麼 | exit gate |
|---|---|---|
| 1-1 | 掃描 | `traces.md` 與 `transcript.txt` 存在 |
| 1-2 | 抽選材信號 | `signals.md` 存在 |
| 2-1 | 列出全部候選 | `candidates.json` 每項五個信號齊全 |
| 2-2 | 合併 | 候選 ≤10 項；每個合併後的項目寫得出共同標題 |
| 2-3 | 分層 | `candidates.py` 跑出三層，`layered.json` 存在 |
| 3 | 決定每項寫什麼 | 呈現層項數＝`layered.json` 的呈現層項數；每項都有 `gaps` 與 `concepts` |
| 4-1 | 寫 JSON | `validate_log.py` **0 error**；`items`／`record` 已照分數由高到低排序 |
| 4-2 | 驗證溯源 | `verify_evidence.py` 通過，原文已進 `_private/` |
| 4-3 | 渲染＋可讀性檢查 | `render.py` 產出 HTML＋MD；`check_readability.py` 跑過（warn 可放行） |
| 4-4 | 推進游標 | 正常模式已跑 `collect_day.sh --commit` |
| 5 | 印候選表 | 候選表已印（全部候選，含被降級的）；邊界項已進記錄層 |
| 6 | 回報 | 只印產物路徑＋候選表；有 warn 放行或缺漏才加第三塊 |

**失敗路由**：
`validate_log.py` 有 error → 回 Step 4-1；
`verify_evidence.py` FAIL → 回 Step 4-1 改引文（**不要改腳本**）；
使用者推翻分層 → 回 Step 5-3 改 JSON 重渲染，**不要重跑掃描**。


### Step 1-1 — 掃描

```bash
bash .claude/skills/daily-log/scripts/collect_day.sh [日期] [--force] [--since <ISO>]
```

產出 `.worklog_scan/<date>/`（在專案根底下）：

| 檔案 | 內容 |
|---|---|
| `traces.md` | git commits、未提交變動、當天新增/修改的檔案、新圖、`.meta.json`、結果表前幾行、STATE.md/log diff |
| `transcript.txt` | 當天對話（已剝除工具輸出） |
| `transcript_user_only.txt` | 只有使用者訊息，約 1/5 大小 |
| `session-manifest.json` | 機器可讀的 session 清單（id、project、起訖、訊息數）。Step 4-2 的溯源驗證以它為準 |

**先完整讀 `traces.md`**（檔案層的客觀事實），再讀 `transcript_user_only.txt` 掌握脈絡與決策點，
需要推導細節時才回讀完整 `transcript.txt`。

若是增補模式，**同時讀既有的 `.data/<date>.json`**，知道哪些已經寫過了，不要重複記。

### `transcript.txt` 裡有什麼、沒有什麼

保留：對話全文、**工具指令列**（截 300 字元）、**工具結果前 15 行**（每行截 200 字元）。
丟棄：`thinking`（未定案的推測，留著會讓人把「試過的」當成「結論」）、圖片。

> **為什麼要留工具輸出**：舊版整批丟掉，理由是「檔案層的事實由 git 掃描負責」——
> 但**專案不見得是 git repo**（原始場景的專案有半年不是），那個負責的人不存在。
> 等於最硬的證據（實際跑的指令、實測數字）被丟了，
> 日誌能不能寫對，取決於「當時有沒有在對話裡順口講出來」。
> 實例：某天的結論是「這批輸入缺一個必要欄位，所以不能用」，
> 而它唯一的原始證據是一張驗收表裡的一格 —— 那張表只存在於 `tool_result` 裡，
> 對話正文從頭到尾沒有複述過那個值。

### ⚠️ 重疊區不是素材

檔頭會標出**重疊區**（游標往前 60 分鐘）與**本次新增**兩段，重疊區的每一段標題都有「〔重疊·已讀過〕」。

重疊區存在的理由是：斷點幾乎都落在工作中間（人是做到一半才寫日誌），
沒有前文會看不懂後面在做什麼。**它只用來接上前文，不要從裡面挑新的工作項** ——
挑之前先比對既有 `.data/<date>.json` 記過沒有。

### ♻️ resume 造成的重複（已自動處理，但要知道它存在）

`--resume` / `--continue` 恢復對話時，Claude Code 會**開一個新的 session 檔、把先前的歷史整段複製進去**，
舊檔留著不動 —— 同一則訊息在兩個檔案各有一份，uuid 相同。**這不是 bug，是存檔方式。**

原始場景出現 6 次，約每 1~2 週一次（其中一次是 452 則全數重複於另一個 session 檔）。
**時間過濾擋不住**——兩份的時間戳一模一樣。

`extract_transcript.py` 已按 uuid 去重（平手時保留全檔訊息較多的那份，另一份是純前綴複本），
去掉幾則會印在終端與 transcript 檔頭。
⛔ 沒去重的後果：同一條指令與輸出出現兩次 → 記成兩個工作項，或誤判某件事花了雙倍時間。

### session 一覽表要看

檔頭有一張表列出本區間的每個 session 及其所屬 **project**。
掃的是 `~/.claude/projects` 底下**全部** project 目錄（舊版寫死幾個，
在別的路徑啟動 Claude Code 就會靜默漏掉整段工作），所以**可能撈到與本專案無關的 session**
——看 project 欄，判斷時排除。

### Step 1-2 — 抽選材信號

```bash
python3 .claude/skills/daily-log/scripts/signals.py <日期>
```

產出 `.worklog_scan/<date>/signals.md`：逐則使用者訊息（拍板句標 ★）、寫入型工具呼叫、
git commit、動過的檔案（mtime ∪ git commit 記錄）、**subagent 報告提到的檔案**、前 7 天的日誌標題。

### ⚠️ 落地信號有兩個結構性盲點

兩個都會**無聲漏掉整個工作項**，不是漏一個檔而已：

| 盲點 | 為什麼 | 現在怎麼補 |
|---|---|---|
| **mtime 只記得最後一次改動** | 補寫舊日期時，那天改過、之後又被改過的檔（專案現況、決策紀錄這類最活躍、也最該記的檔）在時間窗裡已經消失 | traces.md 對 `watch-paths` 走 git log、另加「commit 動過的檔案」；signals.md 取兩者聯集，只有 git 看得到的標 **[git]** |
| **subagent 的內部工具呼叫不進 transcript** | 主對話只留結案報告，沒有那些 Edit 指令 → `寫入型工具呼叫` 抓不到 | signals.md 新增 `2d. subagent 報告提到的檔案`，從報告正文撈路徑 |

實例：兩個 subagent 改了專案現況與決策紀錄兩份文件，
兩個盲點同時生效 → 那件事**連候選都沒進去**，使用者事後才發現。

**所以列候選時 `2c` 與 `2d` 都要看**，尤其 `2d` —— 它代表的常常是當天最有份量、
你自己沒動手所以印象最淺的那幾件事。

⚠️ **`2d` 是提醒，不是清單。** 它撈的是 subagent 報告裡**提到**的路徑，
分不出「改了它」和「引用了它」——盤點型的 subagent 會列出一整串它只是讀過的檔。
實測：某天撈到的 42 個裡有 3 個那天根本沒被動過；另一天的 182 個還混進了專案外的唯讀路徑。
**用法是「有沒有漏掉工作項」，不是「這些檔今天被改過」**；要分辨就跟 `2c` 交叉比對。

📌 **三個落地信號互為備援，缺一個不必然出事，缺兩個就會。** 實測三天：

| 日期 | mtime ∪ git | subagent 報告 | 主對話工具呼叫 | 結果 |
|---|---|---|---|---|
| 第 1 天 | ✗ | ✓ | ✓ | 有涵蓋 |
| 第 2 天 | ✗ | ✗ | ✓ | 有涵蓋 |
| 第 3 天 | ✗ | ✓（修好才有） | ✗ | 修好前**全盲**，漏掉整個工作項 |

三天的 mtime 全部失效（那幾個活躍檔的 mtime 都已被後來的改動覆蓋）——
**補寫舊日期時不要把 mtime 當主要信號。**

它只把**可數的東西數出來**；哪個候選對應哪些訊息與檔案要你讀 transcript 判斷。

**exit gate**：`signals.md` 存在，且使用者訊息數不是 0（是 0 代表過濾器把人講的話也濾掉了，先查 `NOT_HUMAN`）。

### Step 2-1 — 列出候選項（**全部**，不先篩）

⚠️ **這一步不做取捨。** 把當天所有「有頭有尾的事」都列成候選，
包含你覺得不重要的、agent 自己跑的、純工具維護的。取捨由 Step 2-2 的合併與 Step 2-3 的分層規則做。

**唯一排除的**：環境設定、套件安裝、路徑找不到、shell 除錯、指令打錯重打、閒聊。
這些連候選都不算。

#### ⚠️ 強制候選：翻案（推翻／下修／撤回先前的結論）

**今天把先前某個結論推翻、下修、或決定不採用 → 一律列成候選，而且不得只併進別項的
`details`。** 就算它只改了一個檔、只講了兩則，也要獨立列出來。

**為什麼要特別寫這一條**：五個選材信號都在量「今天發生了什麼」，
而翻案的本質是「**某件事以後不會再發生了**」——它通常只改一個檔（把結論寫進現況文件）、
討論也短（想通了就下結論），所以五個信號**天生抓不到它**。

**代價是實測過的**（不是設想出來的風險）：某天的 headline 把一個發現列為當天重大進展，
`interpretation` 寫「**它改變了下一步該用哪份輸入**」；
**隔天就下修強度、並決定不更換**，而那個決定**沒有進任何一天的日誌**。
下游的週報工具因此把一件已經撤下的事判成當週主線——它的推論沒錯，是輸入缺了一半。

**怎麼認出翻案**：出現「其實不用改／不換／強度下修／原本以為…但／這條路先擱著／
判斷錯了／不是 bug 是既成事實」這類語句，或 `watch-paths` 的現況文件裡某段被改寫成
「已解除／已下修／作廢」。

翻案項在候選表上標 `[翻案]`，**最低進記錄層**，不得默默消失。

每個候選要填五個信號（來源是 `signals.md`）：

| 信號 | 怎麼填 |
|---|---|
| `user_msgs` | 這條線牽涉幾則使用者訊息 |
| `decision` | 這條線上有沒有拍板句（`signals.md` 標 ★ 的那些） |
| `files` | 這條線改了幾個檔。**用 `signals.md` 的「寫入型工具呼叫」那份**（帶 session id，歸屬得到），去重後計數 |
| `commit` | 有沒有對應的 git commit |
| `continued` | 前 7 天的日誌提過同一件事嗎 |
| `kind` | 這件事屬於哪一類（見下表）。判不出來就填 `capability` |

⚠️ **平行開多個 session 做不同任務時**（`signals.md` 會在開頭警示），
先照 session 分組再對應到候選。兩件要注意的事：

- **`files` 只能用「寫入型工具呼叫」那份算**（帶 session id）。
  `traces.md` 的 mtime 變動與 git commit 是**全域**的，分不出哪個檔是哪條線改的——
  用它會把 A session 的檔案數算到 B 的候選上。
- **同一件事跨 session 做**（在 A 起頭、在 B 收尾）要合成一項，
  合併判準見 Step 2b：「同一條完整的依賴鏈即使跨檔案、跨 session，也該考慮合併」。

| `kind` | 意思 | 例子 |
|---|---|---|
| `method` | 專案的主線工作：方法、資料、分析、結果 | 換參數重測、建測試集、查證某個數字的來源 |
| `capability` | 讓之後能做更多事的工具、腳本、規則、文件系統 | 改日誌 skill、寫分析腳本、訂寫作規則 |
| `infra` | 讓環境能跑或更安全的設定 | 納入版控、改 hook、裝套件、修路徑權限 |

`infra` 是**扣分**的。實測依據：第一次實跑時「把專案納入版控」與
「收緊一個安全性設定」拿到全場最高分（各 10 分），但那兩件事使用者明確不想講；
而當天最大的產出（改 18 個檔）只有 6 分。三個信號都判不出類別，
而類別正是取捨依據——沒有人的日誌是要講「我裝好了版控」。

### Step 2-2 — 先合併，再分層（★ 這一步比分層更影響結果）

**候選超過 10 項就一定要回頭合併一輪。** 一個工作項是「一件有頭有尾的事」，
不是「這件事的一個面向」。

#### 合併判準：符合 **兩條以上**才合併

1. **推進同一個目標** —— 合併後能回答同一個問題
2. **在同一條依賴鏈上** —— 一個是另一個的前置、驗證、或消費端延伸
3. **共同形成同一個交付物或同一個決定**
4. **會被寫進週報的同一頁** —— 週報一頁只講一個重點，這是最貼近下游的判準

#### 驗證：寫得出共同標題嗎

合併之後**必須寫得出一個說得出共同目標的標題**。寫不出來，就代表它們不是同一件事，拆回去。

| ❌ 拆太細 | ✅ 合併後 |
|---|---|
| 「評估新資料源能不能用」「照舊配方建它的參數檔」「開跑第一批處理」 | 「把新資料源接成第二個獨立來源：評估 → 建參數檔 → 開跑」 |
| 「方向改為先做特徵工程」「寫特徵登記表並算完 18 個樣本」 | 「改成特徵工程優先，並產出 20 個特徵的登記表與特徵表」 |

#### 不算合併理由

同一天做的、同一個檔案、同一個 repo、都是「修 bug」或「寫文件」這類同一種動作、名稱相似。
**這些是巧合，不是同一件事。**

#### 不該合併

讀者需要為它們做**不同的決定**、各自有**獨立的結論或數字**、彼此**沒有依賴關係**。
反過來，同一條完整的依賴鏈即使跨檔案、跨 session，也該考慮合併。

#### 合併後信號怎麼算

| 信號 | 怎麼合 |
|---|---|
| `user_msgs` | 相加 |
| `files` | 相加後**去重**（同一個檔被兩項碰過只算一次） |
| `decision` / `commit` / `continued` | 任一為真即為真 |
| `kind` | 取最高：`method` > `capability` > `infra` |

分數因此變高是對的——**一件大事本來就該排前面**。

> **為什麼要往「粗」調**：我們的日誌**不是最終產物**，週報才是，而週報一頁只講一件事。
> 切太細會讓呈現層的 5 個名額被同一件事的不同面向佔滿，把真正該講的別件事擠出去
> （實測：一件事被切成 5 項，佔掉 5 個名額的絕大多數）。
> ⚠️ 若你的日報**本身就是最終產物**（不再往上彙整成週報），那該切得比這細得多——
> 這條粗細是為「日誌是週報的原料」這個用途定的。

### Step 2-3 — 分層

```bash
python3 .claude/skills/daily-log/scripts/candidates.py \
    .worklog_scan/<date>/candidates.json --json .worklog_scan/<date>/layered.json
```

⚠️ **增補模式（同一天跑第二次）要加 `--append`**，把先前那次的分層併進來。
不加的話 `layered.json` 只涵蓋本次的新候選，而 `.data/<date>.json` 的 `items` 是**累加**的
→ Step 4-1 的項數比對會誤報 error。

規則寫在腳本裡（權重、門檻、5 項上限、commit 保底），**不要自己另外判**——
規則在程式裡才可稽核、才不會每天漂移，也才能一次調完對所有日子生效。

輸出三層：

| 層 | 去哪 | 意思 |
|---|---|---|
| **呈現** | JSON 的 `items[]` | 給人看的最多 5 項，套全部寫作原則 |
| **記錄** | JSON 的 `record[]` | 給 agent 爬，渲染成頁尾折疊區。要通順，但不必四段、不必配圖 |
| **邊界** | JSON 的 `record[]`，並在候選表上標出來 | 分數落在交界。**一律進記錄層**，但要顯示在候選表上讓人看得到 |

⚠️ 權重與門檻**未經校準**，是設計時定的起點。改它要在 `references/` 記下依據。

**exit gate**：三層都分好，`layered.json` 存在。呈現層最多 5 項（無下限）。

### Step 3 — 每一項要寫什麼

⛔ **這一步不得新增、拆分或合併呈現層的項目。** 寫進 `items[]` 的就是
`layered.json` 判給呈現層的那幾項，一項對一項。

覺得某一項該拆成兩項（或兩項該合成一項）→ **回 Step 2-1 改 `candidates.json`
再重跑 `candidates.py`**，讓新的組合重新分層、重新出現在候選表上。

> **為什麼要擋**：分層規則只作用在候選表上。Step 3 一旦能憑空多寫一項，
> 那一項就**沒有經過任何規則、也不會出現在 Step 5 的候選表** ——
> 使用者根本沒有機會否決它。
> 實例：某天的候選表印 4 項，成品是 4 個呈現項＋1 個記錄項，
> 多出來的那項使用者明確表示只想放記錄層。
> `validate_log.py` 現在會比對兩邊的項數，多出來直接 error。


**呈現層的項目**（`items[]`）：`question` / `approach` / `result` / `interpretation` 四段，
加上 `gaps`（還缺什麼）、`artifacts`（碰過的檔案／指令／產出）、`concepts`（術語＋白話）。

- `gaps` 是**強制欄位**，真的沒有才寫「無」。標成 `done` 的項目讀起來像結案，
  但實際工作裡幾乎沒有真的結案的項目，限制本來就是內容的一部分。
  ✅「最低的那一組輸入完全沒測過」　❌「還有很多要做」
- `concepts` **不渲染**，但要寫。它逼你把每個詞翻成白話一次——
  **翻不出來，代表那句話本身要改寫**。寫完存進 JSON 給週報用（過去這行寫完就丟）。
- `artifacts` 只放**實際碰過的**，不要編。它是下游週報工具的原料索引。
- **圖**：數字有比較關係（多組對照、隨 TF 變化的趨勢、門檻與樣本分數的相對位置）
  就配圖，單一數字或純敘述不用。每一項都要判斷一次。

**記錄層的項目**（`record[]`）：`title` / `what` / `why_demoted` / `artifacts` / `evidence`。

⚠️ **`what` 是記錄層的本體，要把這件事講完**——why（為什麼做）、did（做了什麼）、
result（關鍵數字或結果）、state（結束在什麼狀態）四件事都要有。
自由文字即可，不必拆欄位。參考長度 **100~300 字**，少於 60 字會被 warn。

**不必**打磨標題、不必把術語換白話、不必配圖、不必寫「所以呢」。
兩層的分工是**打磨程度**，不是資訊量：
呈現層＝挑重點寫到好讀；記錄層＝其餘的把事實寫齊，**難看沒關係**。

> 讀者的 agent 讀不到 `artifacts` 指向的原檔（那在另一個 repo），
> **`what` 寫的東西就是他能拿到的全部**。

**exit gate**：呈現層項數與 `layered.json` 的呈現層一致；每一項都有 `gaps` 與 `concepts`（真的沒有才寫「無」）。

### Step 4-1 — 寫 JSON 並渲染

依 `references/log_schema.md` 寫日誌 repo 的 `.data/<date>.json`。

⚠️ **`items[]` 與 `record[]` 一律照 `candidates.py` 的分數由高到低寫入。**
分數最高的排第一，頁面上就會出現在最上面。`render.py` **不再重新排序**——
它照 JSON 的順序渲染，所以順序寫錯就是頁面錯。

> 分數不進 JSON（那是啟發式，寫進去下游會當客觀量用），
> 但**順序本身就把排名帶過去了**。
> ⚠️ 校準時改：舊版渲染時把 `kind: "tooling"` 的項目一律排到最後，
> 那會蓋掉分數順序——最重要的一項可能因為被標成工具類而掉到最下面。
> 分數已經含類別加權（研究 +3／能力 +2／環境 −3），研究項自然排前面，不必再排一次。

- **增補模式**：讀進既有 JSON → 追加新 items → 更新 `headline`（要涵蓋一整天，不是只講新增的那段）→ 寫回
- 更新 `scan.last_scanned` 為 Step 1-1 印出的掃描終點，`scan.sessions` 併入本次的 session id
- 要放圖時，**先把圖複製進日誌 repo 的 `daily/figures/<date>/`** 再引用（絕不引用 `results/` 的路徑）；
  JSON 裡寫相對於 `daily/` 的路徑，即 `figures/<date>/xxx.png`
- 簡單的長條／折線／數線圖直接手寫內嵌 SVG；matplotlib 已產好的 ROC、heatmap 就複製 PNG
- **記錄層寫進 `record[]`**（Step 2-3 判為「記錄」的那些），`advisor` 只在掃到讀者提問／方針時填
- 寫完先跑結構檢查，**有 error 不要往下走**：

```bash
python3 .claude/skills/daily-log/scripts/validate_log.py <日期>
```

### Step 4-2 — 驗證溯源（★ render 之前跑，不可跳過）

每個 item 都要有 `evidence`，裡面是**從 `transcript.txt` 逐字複製**的引文（欄位規格見
`references/log_schema.md`）。寫完 JSON 之後、render 之前跑：

```bash
python3 .claude/skills/daily-log/scripts/verify_evidence.py <date>
```

它在逐字稿裡定位每一段引文，把 `session_id` / `ts` / `line` **回填**進 JSON；
找不到就 FAIL 並且不改檔。

**為什麼位置要由腳本查、不由你填**：自己填的 session id 填錯了沒有任何機制看得出來。
改成「只抄引文、位置用查的」之後，`[FAIL] 在逐字稿裡找不到` 就是捏造或改寫的訊號——
編出來的句子不會剛好出現在原文裡。

三種會被擋下來的寫法：

| 訊息 | 意思 | 怎麼修 |
|---|---|---|
| `在逐字稿裡找不到` | 引文是改寫或憑印象重述的 | 回 `transcript.txt` 原樣複製 |
| `引文太短` | 少於 12 字，在逐字稿裡到處命中 | 往前後多抄一句 |
| `命中 N 處`（warn，不擋） | 引文不夠獨特 | 想精確定位就加長，否則可放行 |

⚠️ **通過只代表有據可查，不代表結論正確。** 這支不檢查「引文是否支持這一項的結論」，
那一層仍然要自己看。

**exit gate**：`verify_evidence.py` 通過，原文已搬進 `.data/_private/`（主檔不再有 `quote`）。

### Step 4-3 — 渲染與可讀性檢查

```bash
python3 .claude/skills/daily-log/scripts/render.py <date>
python3 .claude/skills/daily-log/scripts/check_readability.py <date>
```

`check_readability.py` 抓**名詞化的標題**與「標題＋摘要黏在一起」，全部是 warn。
有提醒就改 JSON 重渲染；判斷是誤判而放行的，在 Step 6 說明是哪一項。

⚠️ 它抓不到**沒定義的詞**（「取代率降低了」是一句話，但那個詞沒交代）。
那一層靠 `references/writing-rules.md` 的對照表與 `concepts` 欄位。

**exit gate**：HTML＋MD 都產出，`check_readability.py` 跑過。

### Step 4-4 — 推進游標

**render 成功之後，一定要推進游標**：

```bash
bash .claude/skills/daily-log/scripts/collect_day.sh --commit
```

⛔ **沒 commit 游標就不會前進**，這是刻意的：掃了卻沒寫成日誌（中途放棄、被打斷）時，
那段素材下次還在，不會像舊版那樣無聲消失。反過來說，**寫完了卻忘記 commit，
下次就會重讀同一段** —— 所以這一步不能省。

補寫模式（指定日期）與 `--since` 不動游標，不需要 commit。

### Step 5 — 印候選表（不問問題）

**全自動。跑完就結束，不問任何問題。**

> 校正期跑完連續五天之後，選材與版面都不需要再修正，
> 所以早期那道「一行回覆否決」的關卡拿掉了 ——
> **設計目標本來就是全自動**（工作一整天了，不該再回答問題）。

把 `candidates.py` 印出來的表原樣貼給使用者，當作 Step 6 回報的一部分：

```
 1. 過濾器改用留一法重測      [呈現]  你12則・有拍板・改3檔・續・研究  (12分)
 5. 輸入換成帶完整欄位的那批  [邊界]  你2則・有拍板・改0檔・新・研究  (9分)
 8. 週報 CSS 調整             [記錄]  你0則・改2檔・新・能力  (4分)
```

⚠️ **全部候選都要在上面，含被降級的。** 它不是要人回答，是**讓判斷可稽核**——
使用者看得到哪一項被降級、憑什麼，隨時可以一句話推翻。藏起來就沒有這個機會。
⚠️ **要顯示原始信號，不是只給分數。** 分數看不出為什麼，信號看得出來。

**邊界項一律進記錄層**，`why_demoted` 寫明「落在邊界」。

> 為什麼預設是記錄層而不是呈現層：呈現層有名額上限，
> 把不確定的項目塞進去會擠掉確定該講的；而記錄層無上限，
> 放錯的代價只是多一段文字。**不確定時往資訊留得住的那邊放。**

⛔ **不要問任何問題。** 框架、主軸、主角、優先權由分層規則決定；
放棄的路對話裡看得出來（出現「這個不用了」「改用 X」）就直接寫成 `status: "dropped"`；
指導回饋掃到才記（進 `advisor`），掃不到留空。

#### 使用者主動給回饋時怎麼處理

不是每次都會有。**他主動說了才做**：

改 JSON、重跑 `validate_log.py` 與 `render.py`。**不要重跑掃描。**

同時處理兩件事：
1. 寫進 `~/.config/daily-log/feedback.md`（日期｜哪一項判錯｜使用者說該怎樣｜改了什麼｜skill 版本）
2. 判斷這是**規則**還是**偏好**——兩問都過才算規則：
   ① 換一個使用者、換一個專案主題，這條還成立嗎？
   ② 這條在其他日子也成立嗎？
   兩問都過 → 改分層權重或 SKILL.md，並在 `references/` 記依據；
   否則 → 進 `preferences/<使用者名>.json`，不動公版規則。

⚠️ **一輪最多改 1~2 條規則**，且改完要對先前跑過的日期重跑一次，
看舊判斷有沒有變壞。逐日調參最常見的死法不是過擬合，是「修好 A 弄壞 B」而沒人發現。

### Step 6 — 回報（★ 保持乾淨）

**預設只有兩塊**：產物路徑、候選表。

```
→ <日誌 repo>/daily/2025-01-15.html（呈現 3 項／記錄 2 項）

 1. 改成特徵工程優先，並產出 20 個特徵的登記表      [呈現]  你28則・有拍板・改9檔・續・研究  (17分)
 2. 把新資料源接成第二個獨立來源                    [呈現]  你17則・有拍板・改29檔・新・研究  (15分)
 3. 把方向轉向寫進專案現況文件                      [呈現]  你3則・有拍板・改5檔・續・能力  (13分)
 4. 把解釋風格訂成一條規則                          [記錄]  你1則・改2檔・新・能力  (7分)
 5. 寫當天日誌並推上                                 [記錄]  你3則・有拍板・改0檔・續・能力  (7分)
```

**第三塊只在真的有事時才加**，沒事就不要寫：

| 什麼時候加 | 寫什麼 |
|---|---|
| 有 gate 的 warn 被你判斷放行 | 哪一項、為什麼放行 |
| 某個數字查不到出處、某項只能標 `ongoing` | 哪一項、缺什麼 |
| 你做了規格沒涵蓋的判斷 | 做了什麼、依據是什麼 |

⛔ **不要寫的東西**：
- 「三個檢查全過」——全過是常態，報它等於沒資訊
- 「這輪吃到哪些新規則」——規則是常駐的，不是每天的新聞
- 把每項的 `gaps` 再複述一次——那已經寫在頁面上了
- 「不開表單」「不用回」之類的話——**這個 skill 不問問題**，不必宣告

**不要自己 git commit 或 push**，除非他明確要求——推上去讀者就看得到，那是他決定的時機。
他要推的時候，在日誌 repo 底下 `git add -A && git commit && git push`。

## 寫作規則

📄 **`references/writing-rules.md`** —— 術語策略、標題怎麼寫、否定誤解的四拍、
結構與數字的擺法、成品框架。**寫呈現層的項目之前讀它。**

三條最常被違反的，放在這裡當提醒：

1. **術語能換就換掉。** 你的領域專有名詞保留（讀者本來就懂那些）；
   「取代率」「洩漏」「時間窗對齊」這種中文抽象簡寫換成白話。
   ⚠️ **不要寫解釋句當第二層**——標題本身就要說清楚。
2. **標題寫成一句話，可以是問句。** 唸出來如果是「一個東西的名字」就改寫。
3. **`headline` 寫結論，不寫做了什麼。**
   ✅「快取改用 LRU 之後命中率從 0.62 拉到 0.88」　❌「今天測試了快取設定」

記錄層（`record[]`）不套這些——通順就好。

## 與專案內部文件的分工

日誌記「**當天發生什麼**」給外部讀者看。專案內部通常另有兩種文件：
記「**現在什麼是對的**」的現況文件、記「**當時為什麼那樣判斷**」的決策紀錄，
那兩種是給接手的人／agent 看的。**讀者不同，不互相取代。**

**這個 skill 只寫日誌，不寫那兩種**——別讓它順手去改專案文件。
但若當天有東西定案了，在日誌裡標出來，方便之後回頭對照。

> 你專案裡那兩種文件的路徑，寫進 `~/.config/daily-log/watch-paths`，
> 掃描層就會特別 diff 它們（它們的 mtime 最容易被後來的改動覆蓋）。
